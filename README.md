# AMML Ranking Competition 2026 — neural rank ensemble

**Итог:** 10-е место на Private Leaderboard. **Public NDCG@10 = 0.964651**, **Private NDCG@10 = 0.967919**. Финальная отправка — `submission_fusion_rank_mean.csv` из ноутбука `notebookdcc3eaf112` (версия `Rank_Fusion`).

## 1. Задача и данные

По каждому русскоязычному поисковому запросу ранжируется исходный набор фрагментов. Дано 31 530 размеченных пар (3 042 запроса) и 13 507 тестовых пар (1 305 запросов). Метрика — среднее **NDCG@10 по запросам**, при равных оценках сортировка по строковому `id`. Все исходные кандидаты должны остаться в итоговом файле. Обучение выполнялось **исключительно на размеченных данных соревнования**; публичные предобученные веса разрешены, внешние обучающие корпуса не использованы.

При подготовке текстов применялись нормализация Unicode, удаление лишних HTML-артефактов и пробелов, восстановление недостающих заголовков по однозначно сопоставленным `article_id`, отбор контекста длинных фрагментов. Поля `query_id`, `article_id`, `document_id` использовались для формирования групп, восстановления заголовков или контроля данных, а не как target-encoded признаки. Разделение train/validation — **GroupShuffleSplit по `query_id`**, без пересечения запросов. Qwen seed `2028`, Jina seed `731` (эти валидационные наборы отличаются, поэтому их общая часть содержит 79 запросов).

## 2. Финальная архитектура

1. **Qwen3-Reranker-4B** и **Qwen3-Reranker-8B**: обучены QLoRA на тренировочных парах (4-битная NF4-квантизация, LoRA rank 16, alpha 32, dropout 0.05). Обучение сочетает бинарный BCE и попарный ranking loss. Сохранено лучшее состояние на валидации. Финальная Qwen-ветвь использует сохранённые адаптеры после **дополнительного инференса v6**, а не новые шаги обучения v6.
2. **Jina-reranker-v2-base-multilingual**: обучен на полных группах запросов (`rerank`, weighted pairwise loss + BCE + listwise). Затем получены две дообученные версии: **Jina A** продолжает первый checkpoint, **Jina B** независимо обучается от исходного Jina.
3. Две дополнительные **инференс-проекции** уже обученных Jina: `body` (без заголовка, max 384), `long` (заголовок + текст, max 512, веса Jina B).
4. **Финальный Rank Mean:** Qwen v6 получают z-нормализованный скор на каждый запрос. Для пяти Jina (`old`, `a`, `b`, `body`, `long`) их сырые выходы предварительно z-нормализуются внутри запроса, далее для каждого кандидата рассчитывается ранг по убыванию, усреднённые ранги (`method="average"` для равных значений), отрицательный ранг снова z-нормализуется внутри запроса. Среднее пяти Jina добавляется к Qwen v6 с коэффициентами **0.5 / 0.5**. Это ровно формула финальной отправки; **не** RRF и **не** Median.

Обучение Jina QA на одном из промежуточных этапов было отдельным экспериментом, но финальный вес QA равен нулю, поэтому повторное обучение QA **исключено** из итогового воспроизведения.

## 4. Ablation Study и статистика

На 378 Jina-only валидационных запросах: равновесный Equal GPU ~0.947832, Median ~0.953294, RRF ~0.951944, Rank Mean ~0.948972. На 79 общих запросах Qwen + Jina: Equal GPU ~0.944766, Rank Mean **~0.955617**, RRF ~0.951323. На общем holdout метрики оценивают не независимые новые данные: те же запросы неоднократно использовались для анализа и выбора подходов.

Для сравнения использовался **paired bootstrap по `query_id`**, 20 000 повторений. Доверительные интервалы разностей NDCG@10 для некоторых сравнений пересекали 0, в том числе Rank Mean относительно Equal GPU; множественные сравнения без поправки не дают оснований заявлять строгую значимость улучшения. Подбор весов/формулы на валидации и Public Leaderboard мог дать оптимистическую оценку. Результат на Private (+0.003268 к Public для финальной модели) — наблюдение, а не гарантия точного повторения при переобучении.

## 5. Воспроизведение

### Среда

- ОС: **Kaggle Linux x86_64**, Python **3.13**, **Tesla T4 × 2** (в одном GPU-обучающем этапе используется один GPU), CUDA/torch build из исходного Kaggle container `torch 2.11.0+cu130`.
- Основные версии зафиксированы в [`requirements.txt`](requirements.txt). Контейнер должен иметь совместимую с T4 GPU-сборку PyTorch; `pip install` версии только по номеру без соответствующего CUDA backend может привести к CPU-only установке.
- Internet ON при первом скачивании **предобученных** моделей с Hugging Face. Внешние датасеты **не** скачиваются и **не** используются.

### Шаги

1. Создать Kaggle Notebook из [`solution.ipynb`](solution.ipynb), добавить **только CSV оригинального соревнования** и выбрать `STAGE = "check_data"`; выполнить `Save & Run All` (CPU).
2. Для каждой последующей стадии в начале notebook изменить `STAGE` на следующую из списка в его шапке, добавить **только Output предыдущей стадии** (через `Add Input → Notebook Output`) и сохранить новую версию. Внутренняя папка `amml_repro_cache/` копируется на новый запуск, чтобы не потерять адаптеры. Исходный competition input можно оставить подключённым.
3. **Обучающие стадии требуют GPU T4 × 2**; для `qwen4b`, `qwen8b`, `qwen_v6_*`, `jina_fast`, `jina_a`, `jina_b`, `view_body`, `view_long` включить GPU. Для `qwen_combine`, `jina_combine`, `final` ускоритель не нужен.
4. На `STAGE="final"` появится `/kaggle/working/amml_repro_cache/submission.csv` с 13 507 уникальными `id` и конечными численными `prediction`. Проверки строк и идентификаторов встроены.

Пайплайн не использует сохранённые leaderboard-предсказания как входы: на каждой стадии восстанавливаются **собственные обученные веса из предыдущих стадий**. Файлы `.py`, создаваемые при исполнении из ячеек notebook, — временные рабочие файлы; **в GitHub лежат ровно три обязательных файла**. Не подключать сразу несколько outputs одной стадии (это может приводить к повторным совпадениям путей).

**Ограничение проверки:** полная последовательность повторного обучения не была запущена заново в момент подготовки этого репозитория. Исторический результат соответствует сохранённой финальной отправке; из-за fp16/4bit, версии CUDA и возможных недетерминированных операций не следует обещать побитовое совпадение нового CSV. Перед окончательной сдачей нужно выполнить чистый запуск указанной цепочки, проверить целостность всех stages и сравнить переранжирование с историческим submission по идентификаторам.

## 6. Ограничения и честность

- Валидация проведена **по группам запросов**; 79 общих запросов сравнительно мало, интервалы широки.
- Результаты Public / Private нельзя использовать как метки обучения; в наших исходных тренировочных скриптах такого доступа нет.
- Числа `0.964651` и `0.967919` — **наблюдавшиеся** метрики, а не обещание точного балла от нового обучения на другой машине.
- Ноутбук фиксирует именно финальную обучаемую ветвь; прежние гипотезы и неудачные эксперименты документированы только в этом README.
